# Решения по проекту ai-translator

Здесь фиксируются решения, которые влияют на структуру проекта и на которые
будут опираться последующие этапы. Формат — ADR: контекст, решение,
следствия.

## ADR-001. Текстовый перевод не идёт через провайдер синхронного перевода речи

**Контекст.** Базовый провайдер Этапа 1 — `transono::providers::openai::translation`
(синхронный перевод речи). Его протокол принимает только аудио: единственные
клиентские команды — `session.update` и `session.input_audio_buffer.append`,
поля для текстового входа в протоколе нет. Отсюда вопрос: как подать в систему
текст — для режима `script`, отладки, интеграционных тестов и, в перспективе,
для перевода текстовых документов.

**Решение.** На Этапе 1 текст в шину подаётся **напрямую, минуя провайдера**:
источник `src/source/text.rs` разбивает текст на фразы и публикует события
`Translated` (ревизиями, затем финальным событием) так же, как это делал бы
адаптер живой сессии. Провайдер при этом не запускается вообще, поэтому такой
прогон не требует ни микрофона, ни сети, ни ключа API.

**Следствия.**

- вся downstream-часть (шина, приёмники, супервизор, экран, транскрипт)
  проверяется полностью без обращения к внешнему сервису;
- конвейер «текст → провайдер → перевод» на Этапе 1 не реализуется; для него
  потребуется отдельный провайдер текстового перевода (Этап 2);
- при появлении такого провайдера `src/source/text.rs` останется прежним: он
  подаёт текст в шину, и замена касается только источника, который пойдёт через
  провайдера.

## ADR-002. Виртуальное звуковое устройство — сторонний драйвер, а не часть приложения

**Контекст.** Приёмник `virtual_sink` (перевод голоса в виртуальное звуковое
устройство — OBS, Discord, Zoom, vMix) объявлен в конфигурации и на Этапе 1 не
реализован: он честно возвращает `SinkError::Unavailable`. На Linux такой
приёмник делается поверх модуля `transono::ctl::pipewire`, а этот модуль по
природе Linux-only — в `transono` он закрыт условием `#[cfg(target_os = "linux")]`.
На macOS виртуальное звуковое устройство — это **не** часть системного звукового
стека, а отдельный драйвер, который пользователь ставит сам (BlackHole,
Loopback); создать его из приложения нечем.

**Решение.** Реализация голосового приёмника — отдельный этап (Этап 4), и делать
её надо поверх `transono::ctl::Backend`, где для macOS уже появится честная ветка.
На macOS приложение пишет звук в устройство, созданное сторонним драйвером, и
никакого драйвера само не устанавливает. До реализации приёмник остаётся
недоступным на всех платформах — это правильное поведение, а не недоделка.

**Следствия.**

- на macOS в документации называется конкретный сторонний драйвер и способ его
  установки, а приложение только сообщает о недоступности приёмника;
- PipeWire-часть `transono` не попадает в граф зависимостей под darwin: она
  остаётся под Linux-условием, и это проверяется (см. задачу 2 плана порта);
- появление реальной ветки `Backend` для macOS — предпосылка Этапа 4, а не
  Этапа 1.
