# Трансляция перевода в голосовой чат Telegram

Этот документ описывает приёмник `telegram_call` — тот, который подаёт переведённую
речь в голосовой чат группы или в трансляцию канала. Состояние на сегодня: вход в
аккаунт, поиск и создание звонка, вход в него и непрерывная подача звука написаны,
собираются и проверены на уровне модульных тестов; живой звонок ждёт первого входа
аккаунта.

## Чем это не является

- Это **не** Bot API. Бот в голосовой чат не входит: Telegram не пускает ботов в
  звонки, поэтому все методы — MTProto и работают от имени пользовательского
  аккаунта.
- Это **не** голосовые сообщения. Живой звук идёт непрерывно, пока работает
  переводчик: движок забирает кадр каждые 10 мс (480 сэмплов при 48 кГц, 16 бит,
  моно), а в паузах перевода идёт тишина, чтобы соединение не рвалось. Кадр длиннее
  или реже — это пропуски в каждом втором слоте и слышимые щелчки, поэтому размер
  и шаг кадра в приёмнике закреплены этими числами.
- Это **не** единственный получатель звука. Переведённую речь линия всегда играет
  локально, на устройстве из `core.output_device`; приёмники голоса — `virtual_sink`
  и `telegram_call` — получают ту же речь дополнительно. Если нужно вещать молча,
  поставьте `output_device = "none"`: динамики останутся тихими, а звонок получит
  звук.

## Что нужно до первого запуска

1. `api_id` и `api_hash` приложения с <https://my.telegram.org> → API development
   tools. В конфигурацию они не пишутся: только имена переменных окружения.
2. Аккаунт Telegram, который будет вещать. Он должен состоять в группе или быть
   администратором канала с правом «Управление видеочатами» (`manage_call`).
3. Канал или группа, где идёт проверка: `@name` или числовой id.
4. Сессия аккаунта: команда `telegram-login` спрашивает номер, код из Telegram и,
   если включена двухфакторная защита, пароль (без эха). Остаётся только файл
   сессии — он и есть аккаунт, поэтому создаётся с правами `0600` и в репозиторий
   не попадает.

## Порядок проверки

```bash
# 1. Ключи приложения и адрес сессии — только в окружении.
export TELEGRAM_API_ID=...        # из my.telegram.org
export TELEGRAM_API_HASH=...      # оттуда же

# 2. Один раз: вход аккаунта. Номер, код и пароль вводятся здесь.
ai-translator telegram-login -c config.toml

# 3. Работа: перевод и живая трансляция в звонок канала или группы.
ai-translator run -c config.toml
```

Конфигурация приёмника:

```toml
[[sink.voice]]
type = "telegram_call"
enabled = true
chat_id = "@mtl_fest_en_translate"   # канал или группа
api_id_env = "TELEGRAM_API_ID"
api_hash_env = "TELEGRAM_API_HASH"
session_file = "~/.local/state/ai-translator/telegram-user.session"
create_if_missing = true             # начать трансляцию, если её ещё нет
```

## Сборка варианта с трансляцией

Движок — `libntgcalls` (C++ WebRTC, LGPL-3.0). Он грузится **отдельной
библиотекой**, а не вшивается в бинарник: статическая копия приносит в процесс свой
C++ рантайм и свой аллокатор и ломает всё остальное, что в нём работает — даже
когда приёмник выключен. Поэтому `packaging/run-nix.sh` и `packaging/build-linux.sh`
скачивают готовую сборку движка под целевую платформу (`packaging/fetch-ntgcalls.sh`)
и кладут её рядом с бинарником; бинарник находит её по rpath (`$ORIGIN` в Linux,
`@loader_path` на macOS). Готовые сборки движка есть для Linux x86_64, Linux arm64,
macOS arm64 и Windows x86_64 — для них трансляция входит в пакет всегда: фича
`telegram-call` зашита в сборочные скрипты, а не выбирается переменной окружения.
Целей без движка пакеты не выпускают: сборка под Intel-мак сразу отказывается,
поскольку `x86_64-apple-darwin` остаётся без трансляции.

Архив движка закреплён по sha256: `fetch-ntgcalls.sh` знает хеш каждого ассета для
своей версии и отказывается распаковывать файл, который с ним не совпал (код
возврата 4), а для версии без пина отказывается сразу (код 3). Движок — это
библиотека в процессе переводчика, поэтому подмена ассета равна исполнению чужого
кода; при обновлении версии хеши нужно пересчитать и вписать заново.

Крейт `ntgcalls-sys` лежит в `vendor/`: его сборочный скрипт в режиме разделяемой
библиотеки выдавал GNU-ключи линкеру (`--allow-shlib-undefined`, `-rpath`), а
линкер macOS их не знает. Правка — эти ключи только для Linux.

```bash
# Обычный дистрибутив или NixOS — одна команда, она скачивает движок и собирает.
bash packaging/build-all.sh                  # релизные пакеты, всегда с трансляцией
bash packaging/run-nix.sh run -c config.toml # сборка и запуск на NixOS
```

Голая `cargo build --features telegram-call` тоже работает, но тогда движок
скачивается как статическая библиотека и вшивается в бинарник — а этого как раз
делать нельзя (см. выше).

Фича `telegram-call` зашита в сборочные скрипты: `build-linux.sh`, `build-macos.sh` и
`build-windows.ps1` включают её сами, переменная окружения на это не влияет. Поэтому
варианта «пакет без трансляции» больше не существует.

В `.deb`, `.rpm`, `.tar.gz` и `.AppImage` движок лежит рядом с бинарником
(`libntgcalls.so`), в macOS-пакетах — `libntgcalls.dylib`, в Windows — `ntgcalls.dll`.

## Запуск на NixOS

Релизные пакеты собраны на Ubuntu 24.04 для обычных дистрибутивов. На NixOS такой
бинарник стартует только через `nix-ld`, а статический C++ движок внутри него такую
подмену не переживает: процесс падает с ошибкой сегментирования сразу после списка
приёмников. Поэтому на NixOS проект собирается и запускается на месте:

```bash
bash packaging/run-nix.sh run -c config.toml
bash packaging/run-nix.sh telegram-login -c config.toml   # если нужен новый вход
```

Скрипт собирает релизную сборку с фичей `telegram-call` и запускает её из
`nix develop`: оттуда приходят `libpipewire`, `libasound`, `libssl` и C++ рантайм
движка. `FEATURES=` (пустое значение) собирает вариант без трансляции.

Тесты сборки с трансляцией — `packaging/test-call.sh`: он скачивает движок, линкует
сборку против него и прогоняет весь набор, включая тесты движка и приёмника.

## Что проверено

- Вход: MTProto-рукопожатие с ключами приложения проходит, `telegram-login`
  спрашивает номер, создаёт файл сессии с правами `0600` и отказывается работать с
  пустым номером. Проверено и в собранном `.deb` в чистом `ubuntu:24.04`.
- Движок: `cargo test --features telegram-call --test telegram_call_engine`
  поднимает его и получает параметры входа для `phone.joinGroupCall` — `ufrag`,
  `pwd`, `fingerprints`, `ssrc`.
- Звук: упаковщик кадров проверен тестами — секунда речи даёт 100 кадров по 10 мс,
  речь 24 кГц сохраняет длительность при переводе в 48 кГц, амплитуда сохраняется,
  тишина остаётся тишиной, неполный кадр ждёт дополнения.
- Сборка без фичи остаётся чисто-Rust, а конфигурация с включённым `telegram_call`
  останавливает запуск с объяснением, что эта сборка так не умеет.

## Если звонок оборвался

Молчащая трансляция — худший из отказов: со стороны всё выглядит рабочим, а звука
нет. Поэтому приёмник замечает обрыв сам:

- вход в звонок ограничен 30 секундами: если Telegram не ответил, попытка считается
  неудачной, а не висит вечно;
- каждый кадр, который движок не принял, считается; после 20 подряд (пятая доля
  секунды) звонок объявляется мёртвым, аккаунт выходит из него, а приёмник
  возвращает ошибку с причиной — дальше работает супервизор: строит новый приёмник,
  и тот входит в звонок заново;
- отказы пишутся в лог не чаще раза в секунду: сто строк в секунду скрывают причину,
  вместо того чтобы её назвать;
- закрытый канал к движку (задача умерла) тоже возвращает ошибку, а не тихо теряет
  кадры.

Перезапуски идут с удвоением паузы от 0,5 с до 30 с, шесть попыток подряд; если
приёмник до отказа успел поработать, счёт попыток начинается заново.

Логика восстановления покрыта тестами, но настоящий обрыв живого звонка ещё не
воспроизводился: для этого нужен вход аккаунта и звонок в канале.

## Что ещё не проверено

- Живой звонок: вход в настоящий голосовой чат канала и звук в нём. Для этого нужен
  первый вход аккаунта — код из Telegram вводит человек.
- Обрыв звонка на живом канале и восстановление после него.
